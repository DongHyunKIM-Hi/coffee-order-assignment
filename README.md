## 과제 개요

- 다중 인스턴스 환경에서도 안정적으로 동작하는 커피숍 주문 시스템을 구현합니다.
- **평가는 4장의 도전 요구사항 4가지를 기준으로 합니다.** 도전 요구사항은 선택 사항이 아닙니다.

- 기능 없이 서버만 켜지는 시작 프로젝트(Java 17, Spring Boot 4.1.1, Gradle)를 제공합니다.

## 1. 과제 소개

커피숍 주문 시스템을 만듭니다.

1. 메뉴 데이터를 준비하고, 메뉴 목록을 조회할 수 있어야 합니다. 메뉴를 넣는 방법은 자유입니다.
2. 커피는 포인트로 주문합니다.
3. 주문 기록을 바탕으로 최근 인기 메뉴를 보여 줍니다.

이 시스템은 같은 애플리케이션을 여러 개 동시에 띄워 운영한다고 가정합니다. 이하 이를 **다중 인스턴스**라고 부릅니다. 같은 사용자의 요청이 서로 다른 인스턴스로 동시에 들어올 수 있습니다.

![커피숍 주문 시스템 구조](docs/images/coffee-order-overview.svg)

## 2. 시작하기

JDK 17이 필요합니다.

1. `starter-project/`를 IntelliJ에서 엽니다.
2. 서버를 실행합니다. 서버는 `8080` 포트에서 실행됩니다.
   ```bash
   ./gradlew bootRun
   ```

DB, 캐시 등 필요한 의존성과 인프라는 설계에 맞게 직접 추가해 주세요.

## 3. 필수 요구사항

아래 API 4개를 구현하고, 설계 문서를 제출 README에 작성합니다. 설계할 때부터 4장의 도전 요구사항(다중 인스턴스, 동시성, 데이터 일관성, 테스트)을 함께 고려해 주세요.

1. 커피 메뉴 목록 조회 API
2. 포인트 충전 API
3. 커피 주문과 결제 API
4. 인기 메뉴 목록 조회 API

### 3-0. 제출 README에 쓸 설계 문서

아래 내용은 제출 README(제출 저장소 최상위의 `README.md`)에 **반드시 포함해야 합니다.** 여기서 문제는 4장의 다중 인스턴스, 동시성, 데이터 일관성 문제를 말합니다.

- [ ] 설계 내용 (ERD, API 명세서)
- [ ] 설계 의도
- [ ] 선택한 문제 해결 전략
- [ ] 그 전략을 고르기까지 비교하고 분석한 내용
- [ ] 기술을 선택한 이유

### 3-1. 커피 메뉴 목록 조회 API

- [ ] 커피 정보(메뉴 ID, 이름, 가격)를 조회하는 API를 작성합니다.

### 3-2. 포인트 충전 API

- [ ] 포인트를 충전하는 API를 작성합니다.
- [ ] 사용자 ID와 충전 금액을 입력받아 포인트를 충전합니다. 1원은 1포인트입니다.

### 3-3. 커피 주문과 결제 API

- [ ] 사용자 ID와 메뉴 ID를 입력받아 주문하고 결제를 진행합니다.
- [ ] 결제는 포인트로만 할 수 있으며, 충전한 포인트에서 결제 금액(메뉴 가격)을 차감합니다.
- [ ] 주문 정보를 데이터 수집 플랫폼으로 **실시간** 전송하는 로직을 추가합니다.
  - 데이터 수집 플랫폼은 주문 데이터를 받아 분석하는 외부 시스템이며, 실제로는 없습니다.
  - 받는 쪽을 Mock API(가짜 서버)나 테스트 코드로 대신하고, 사용자 ID, 메뉴 ID, 결제 금액을 보내 주세요.

### 3-4. 인기 메뉴 목록 조회 API

- [ ] 최근 7일 동안 인기 있는 메뉴 3개를 조회하는 API를 작성합니다.
- [ ] 메뉴별 주문 횟수가 정확해야 합니다. 동시에 주문이 몰려도 횟수가 빠지거나 중복되면 안 됩니다.

## 4. 도전 요구사항

3장의 API를 설계할 때 아래 4가지를 함께 고려해 주세요.

- **평가는 도전 요구사항 4가지를 기준으로 합니다.**
- 필수 요구사항(API 4개와 3-0의 설계 문서)은 평가를 받기 위한 전제 조건입니다.

1. 애플리케이션을 다수의 서버에서 다수의 인스턴스로 띄워도 모든 기능이 올바르게 동작하도록 설계합니다.
2. 동시성 이슈를 고려해 구현합니다.
3. 데이터 일관성을 고려해 구현합니다.
4. 각 기능과 제약 조건(잔액 부족, 동시 요청 등)이 지켜지는지 테스트로 확인합니다.

- 다중 인스턴스는 설계와 제출 README의 설명으로 평가합니다. 서버를 여러 대 띄우는 실행 구성은 필수가 아닙니다.

## 5. 추가 조건

- 인프라 사용에는 제약이 없습니다.
- API 경로, 요청과 응답 형식, HTTP 메서드(`GET`, `POST`, `PUT`, `DELETE`)는 자유롭게 정합니다.
- 에러 응답과 에러 코드는 자유롭게 정의합니다.

## 7. 제출 방법

- `starter-project/` 폴더 안의 파일이 제출 저장소의 최상위에 오도록 올려 주세요. 저장소를 열었을 때 `build.gradle`과 `gradlew`가 바로 보여야 합니다. 이 장에서 말하는 루트는 이 폴더입니다.
- 루트에 제출 README(`README.md`)를 새로 만들고, 3-0의 설계 문서 전부와 실행 방법을 적어 주세요.
  - DB, 캐시 등 인프라를 사용했다면 인프라를 띄우는 방법(예: `docker compose up`)도 함께 적어 주세요.
  - 평가자는 제출 README의 실행 방법과 API 명세를 그대로 따라 서버를 실행하고 요청을 보냅니다.
- 루트에서 `./gradlew test`를 실행했을 때 모든 테스트가 통과해야 합니다. 테스트에 Docker가 필요하면 제출 README에 적어 주세요.
